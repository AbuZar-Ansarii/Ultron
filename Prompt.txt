# PHASE 2 — Reverse engineer the architecture

Investigate these subsystems in detail.

## A. Application bootstrap and lifecycle

Determine:
- The main entry point and startup sequence.
- How configuration and environment variables are loaded.
- How the GUI, background workers, audio systems, and AI components initialize.
- How shutdown, cancellation, exceptions, and resource cleanup work.

Trace the execution path from application startup to the first completed assistant interaction.

## B. Voice and audio pipeline

Determine:
- How microphone input is captured.
- How push-to-talk and wake-word detection work.
- Which speech-recognition engines are supported.
- How audio is streamed or passed to the language model.
- How generated responses are converted into speech.
- How interruptions, buffering, latency, and errors are handled.
- Whether speech processing can run locally.

Draw the actual audio pipeline using Mermaid.

## C. LLM and provider architecture

Determine:
- How model providers are registered and selected.
- How provider-specific implementations are abstracted.
- How prompts, conversation history, streaming responses, and tool calls are handled.
- How local model servers and cloud providers are configured.
- How failures, timeouts, retries, and unsupported capabilities are handled.

Trace at least one complete request from user input through model inference to the final response.

## D. Agentic tool execution and computer control

Determine:
- Which tools and actions are available.
- How the model requests a tool invocation.
- How arguments are validated.
- How tool execution is dispatched.
- How results return to the model.
- Whether execution loops continue until a task is complete.
- How the application handles failures, dangerous actions, and permissions.
- How browser, desktop, keyboard, mouse, and filesystem actions are implemented.

For each important tool, document its implementation file, function, inputs, outputs, side effects, and required permissions.

Identify whether the system implements genuine multi-step agentic execution or primarily direct tool calls.

## E. GUI, avatar, and visual system

Determine:
- How the PyQt6 application window and HUD are built.
- How the avatar is rendered and animated.
- How lip synchronization, expressions, blinking, and gaze are implemented.
- How UI state reflects listening, thinking, speaking, and errors.
- How UI events communicate with the AI backend.
- Which components can be reused independently of the assistant's core.

## F. Memory and conversation state

Determine:
- How conversations are stored and retrieved.
- Whether memory survives application restarts.
- How context is assembled for each model request.
- Whether long-term, semantic, episodic, or project-specific memory exists.
- How memory is updated, searched, and deleted.
- What limitations exist around context growth and persistence.

Do not assume a feature exists merely because it is mentioned in documentation.

## G. Plugins and extensibility

Determine:
- How plugins or additional capabilities are discovered and registered.
- Whether tools can be added without changing core application code.
- How plugin configuration, validation, errors, and permissions work.
- Which interfaces would be suitable for MCP integration.
- Whether external plugins can execute arbitrary code or access sensitive resources.

## H. Scheduling, background tasks, and observability

Inspect whether the project supports scheduled tasks, proactive notifications, background execution, resumable workflows, structured logging, action history, and task-level progress reporting.

Clearly distinguish existing functionality from features that would need to be implemented.
